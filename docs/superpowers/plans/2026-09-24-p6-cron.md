## What already exists (do not rebuild)

`src/iris_ai/tasks.py` is the **one-off** half of this phase and it is good: `parse_when`
(ISO / relative / shorthand, with the timezone fixed and two real bugs already
fixed in place), `TaskStore` (JSON in `workspace/config/tasks.json`), and a
`TaskScheduler` that re-registers pending tasks as `DateTrigger` jobs at boot,
runs the instruction through the chat graph with `origin="task"` (so a task can
never write durable memory), delivers the reply over Telegram when the channel is
up, and removes the task.

`src/iris_ai/scheduler.py` holds two **hardcoded** recurring jobs — nightly sleep and
the morning brief — with `misfire_grace_time=3600` baked into each.

So P6 is not "build a scheduler". It is: **make recurrence and failure policy
first-class, and give the owner a way to see and change the schedule.**

## Task 1 — Job definitions: interval and calendar, not just one-shot (TDD)

Extend the store from `Task` (one-shot) to a `Job` with an explicit `schedule`
kind, keeping one file and one code path:

| Kind | Fields | Truth |
|---|---|---|
| `once` | `run_at` | the existing `DateTrigger` path, unchanged |
| `interval` | `every` (`"15 minutes"`, `"2 hours"`, `"3 days"`) | `IntervalTrigger` |
| `calendar` | `at` (`"09:30"`), optional `weekdays` | `CronTrigger` |

`parse_every()` joins `parse_when()` as a pure, tested function. A recurring job
**must** declare `session_id` (so its runs share a thread) and is capped by
`cron_max_jobs` so a loop cannot fill the disk with jobs.

Tests (`tests/test_cron_jobs.py`): parse each kind; reject an unparseable interval;
round-trip persistence; a recurring job survives a reload and keeps its schedule;
`once` keeps working byte-for-byte (the existing `tasks.py` suite must stay green).

## Task 2 — Catch-up and misfire policy, stated rather than inherited (TDD)

The vault's rule is that bounds are **explicit and tested**, and today's policy is
implicit: `misfire_grace_time=3600` on the two built-ins, and `register_all()`
silently *drops* any one-off task whose time passed while the process was down.

Make it a declared policy with one name per behaviour:

| Policy | Meaning | Default |
|---|---|---|
| `catch_up` | a missed recurring run executes once, late, and says so | **on** for `calendar`, **off** for short `interval` (a 15-minute job that missed 40 runs must not fire 40 times) |
| `skip` | the missed run is recorded as skipped and not executed | the fallback |
| `expire` | a missed one-off is dropped (today's behaviour, now recorded instead of silent) | one-off |

Every decision is recorded in the turn trace with the job id, so "why did my
reminder not fire" is answerable. The missed-run count is kept per job
(`missed: int`) — the vault's "pre-call detection, then record" applied to time.

Tests: a job whose window passed while down runs once under `catch_up` and is
recorded; under `skip` it is recorded and not run; a one-off in the past is
dropped **and logged**, not silently forgotten; a long gap on an interval job
fires once, never N times.

## Task 3 — `iris cron list | add | rm` (TDD)

The blueprint's CLI surface, in the same read-mostly shape as `iris skills` and
`iris agents`:

- `list` — every job: id, kind, schedule (human-readable), next run, session,
  missed count, and whether it is a built-in (nightly sleep / morning brief).
- `add` — `--every` / `--at` / `--once <time>` with `--instruction`; goes through
  the *same* `parse_every`/`parse_when` and the same store, so the CLI cannot
  create a job the agent could not.
- `rm <id>` — removes by id; refuses a built-in (those are config, not jobs).

`tests/test_cron_cli.py`; the command-set assertion in `tests/test_cli.py` gains
`cron` (and so does the duplicate in `tests/test_skills_cli.py`).

## Task 4 — Trace content policy and redaction (audit G5) (TDD)

Scheduled runs happen with nobody watching, which is what makes this load-bearing
here. Today the trace is metadata-only **by accident** and nothing in `src/`
redacts anything.

- A single `redact()` helper is the only way values enter a trace: it strips
  values that look like credentials (bearer tokens, `api_key=`-style pairs, long
  hex/base64 blobs) and any key whose name contains secret/password/token/key.
- The policy is explicit config: `trace_content` ∈ `metadata` (default) |
  `redacted` | `full`, with `trace_content_sample_rate` for the sampled case.
- Traces gain the fields the vault names and Iris lacks: **`args_hash`** (never
  raw args), model + **version**, prompt hash, guardrail decision, cost per turn.

Tests: a secret in a tool argument never appears in the trace under either
`metadata` or `redacted`; `full` is opt-in and still redacts; the hash is stable
for identical args (which is also what makes loop detection possible later).
